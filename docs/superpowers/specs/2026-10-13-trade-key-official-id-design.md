# 거래 키를 국토부 단지 고유번호로 전환 — 설계

- 날짜: 2026-10-13
- 상태: 설계 승인 대기
- 관련: ADR-015(초안, `docs/adr/015-trade-key-official-id.md`), ADR-011(그룹 PNU 중복 정리),
  ADR-013(행정구역 코드 표준화), ADR-014(K-APT 분양·임대 PNU 경합)

## 1. 배경

### 1-1. 발견 경위

2026-10-13 인스타 value 동작구 카드(PR #313)의 5위 "대방대림 1,313만원/㎡"가 실제로는
**상도1동대림의 거래**로 계산된 값이었다. 게시물을 삭제하고 정정본을 재게시했다(PR #314).

- 거래 키 `apt_seq` 는 `batch/trade/load_trades.py` 가 `f"{sgg}_{apt_nm}"` 으로 만든다.
- 동작구에 "대림아파트" 가 둘이라 한 키 `11590_대림아파트` 에 합쳐졌다.

| 동·지번 | 준공 | 거래 | 국토부 aptSeq | PNU |
|---|---|---|---|---|
| 대방동 501 | 1993 | 600건 | `11590-57` | 1159010800005010000 (대방대림) |
| 상도동 411 | 1995 | 130건 | `11590-85` | 1159010200004110000 (상도1동대림, **매핑 없음**) |

- 키는 대방대림 PNU 에만 매핑돼 상도1동대림 거래가 대방대림 가격·점수·카드에 섞였다.
- value 이상치 규칙(PR #311, 단지 중앙값 ±25%)은 혼입 쪽이 다수라 **진짜 대방 거래(18억대)를 오히려 제외**했다.
  이상치 규칙은 키 혼입을 고치지 못한다.

### 1-2. 규모 (로컬 DB 실측)

| 항목 | 값 |
|---|---|
| 매핑된 거래 키 | 40,250개 |
| 법정동 2개+ 이면서 준공연도 2개+ 인 키 | 432개 · 거래 약 103,924건 |
| 기존 키 1개에 국토부 aptSeq 2개+ (혼입 확정) | 498개 |
| aptSeq 1개에 기존 키 2개+ (이름 변형) | 6개 |
| aptSeq 앞자리 ≠ 내부 시군구 코드 | 331개 (예: 내부 41591 ↔ `41590-1071`) |

혼입 예: `11530_현대`(개봉동·구로동), `41133_현대`(성남 4개 동), `41210_주공12`(철산·하안).
일부는 정상(한 단지가 두 법정동에 걸침, 1·2차 분양)이다.

### 1-3. 데이터 가용성

- `api_apt_seq`(국토부 aptSeq 원본)·`umd_cd`·`jibun` 등은 **2023년 이후 일부 행에만** 있다
  (로컬: 매매 2023~25년 27~33%, 2026년 51% / 2022년 이전 0%).
- 로컬 수치는 **과소 추정**이다 — `batch/sync_from_railway.py` 의 `SYNC_TABLES` 가 이 칼럼들을 옮기지 않는다.
  (같은 이유로 `dealing_gbn` 도 빠져, 로컬 카드 생성의 직거래 제외가 동기화된 행에는 적용되지 않는다.)
- 매매는 `build_year` 가 100% 채워져 있다. 전월세는 `build_year` 칼럼이 없다(API `buildYear` 미수집).
- 국토부 API 는 과거 월 재조회 시에도 aptSeq 를 준다(`batch/trade/backfill_trades.py` 가 이 방식으로 보충).
  전량 재수집은 130개월 × 253구 × 2종 ≈ 6.6만 콜(보조키 900콜/일 기준 약 73일).

## 2. 목표와 범위

- **목표**: 같은 이름의 다른 단지 거래가 한 키로 합쳐져 엉뚱한 PNU 에 귀속되는 문제를 원인(이름 기반 키)부터 제거한다.
- **범위**: 2016년 이후 **전체 이력**(매매·전월세)을 바로잡고, 신규 적재가 다시 섞이지 않게 한다.
- **성공 기준**
  1. 혼입 키가 단지별 키로 분리된다(기준 사례: 대방대림 1993년 600건 / 상도1동대림 1995년 130건).
  2. 매핑이 없던 단지(상도1동대림 등)가 자기 거래를 갖는다.
  3. 신규 거래가 처음부터 단지별 키로 적재된다.
  4. 혼입과 무관한 단지의 귀속은 바뀌지 않는다.
- **범위 밖**: aptSeq 를 한 번도 관측하지 못한 키(최근 거래 없는 오래된 단지)의 숨은 혼입,
  주소 PNU ↔ 기존 매핑 불일치 2,244건의 교정(감사 리포트로만 출력, 별도 백로그).

## 3. 결정 — 거래 키 = 국토부 단지 고유번호 (A안)

| 안 | 내용 | 판단 |
|---|---|---|
| **A** | `apt_seq` = 국토부 aptSeq, 없을 때만 기존 키 | **채택** — 공식 ID 라 재발 감시가 필요 없고 이름 변형도 합쳐진다 |
| B | 혼입 키만 `{sgg}_{name}({jibun})` 로 분할 + 분할 목록 테이블 | 기각 — 두 키 체계 공존, 새 충돌마다 목록 추가(반복 땜질) |
| C | 키 유지 + 매핑에 준공연도 구분 칼럼 | 기각 — 소비자 조인 전면 수정, 전월세에 준공연도 없음 |

소비자(`routers/detail.py`, `routers/dashboard.py`, `routers/sitemap.py`, `services/tools.py`,
`scripts/insta_cards/*`)는 전부 `trade_apt_mapping` 을 거쳐 `apt_seq` 로 조인하므로 키 형식 변경의 영향을 받지 않는다.

## 4. 설계

### 4-1. 키 규칙과 적재

- 키 규칙: aptSeq 가 있으면 `apt_seq = aptSeq`(예: `11590-57`), 없으면 `{sgg}_{apt_nm}`.
  두 형식은 `-` 와 `_` 로 구분된다. **키는 불투명 문자열로 다룬다** — 시군구는 항상 `sgg_cd` 칼럼에서 읽는다(1-2 의 앞자리 불일치 331개).
- 키 결정은 새 모듈의 `resolve_trade_key(sgg, apt_nm, api_apt_seq) -> str` 하나로 모은다.
  매매·전월세 적재(`load_trades.py:94`, `:186`)가 이를 공용한다.
- 전월세 적재에 API `buildYear` 를 추가로 받아 `rent_history.build_year` 에 저장한다(신규 칼럼, NULL 허용 — 과거분은 NULL 유지).
  **구현 전 확인**: 현재 `RENT_COL_MAP`(`batch/trade/collect_trades.py`)에 `buildYear` 가 없다 — 전월세 API 응답에
  실제로 있는지 1회 호출로 확인하고, 없으면 이 항목은 빼고 전월세 추론은 면적 서명만 쓴다(4-3 결과는 동일).
- 중복 판정 UNIQUE(`sgg_cd, apt_nm, exclu_use_ar, floor, deal_year, deal_month, deal_day, deal_amount`)는 키를 쓰지 않으므로 변경하지 않는다.
- 키 문자열을 해석하는 코드 정리: `scripts/register_missing_apartments.py:548` 의 `apt_seq.split("_", 1)[0]` → `sgg_cd` 사용.
  같은 가정이 있는 다른 위치는 구현 계획에서 전수 점검한다.
- **적재 변경은 매핑 변경(4-2)과 같은 배포에 넣는다** — 적재만 먼저 바뀌면 새 키가 매핑 없이 쌓여 상세·점수에서 빠진다.

### 4-2. 새 키(고유번호) → PNU 매핑

원칙: **혼입이 증명된 키만 귀속을 바꾸고, 나머지는 기존 매핑을 상속한다** — `manual_fix`, ADR-011 그룹 PNU 정리,
ADR-014 분양·임대 교체 등 누적된 교정을 잃지 않기 위해서다.

새 키 K, K 를 포함하던 기존 키 L 에 대해:

| 순위 | 조건 | 매핑 | match_method |
|---|---|---|---|
| 1 | K 로 행을 보내는 모든 기존 키 L 중 상속 가능한 것(L 안의 aptSeq 가 K 하나뿐이고 L 이 `apartments` 에 **실존하는** PNU 로 매핑됨)들의 PNU 합집합이 **정확히 하나** | 그 PNU 상속 | `api_inherit_legacy` |
| 2 | 1 실패(L 이 혼입·미매핑·끊긴 매핑, 또는 상속 가능 PNU 가 0개이거나 둘 이상) | 키의 모든 행의 주소 PNU(법정동코드 10자리 + 산 여부 + 본번 4 + 부번 4) 중 `apartments` 에 있는 것이 정확히 하나면 그것 — 넣은 직후 물리 게이트(`mapping_gate`)를 통과해야 남는다 | `api_address_pnu` |
| 3 | 1·2 실패(게이트 거부 포함) | 매핑하지 않음(fallback 없음) — 배치 로그에 개수와 목록, rekey 는 해당 행을 이름 키로 되돌려 현상 유지 | — |

- 주소 PNU 의 산 여부 자리: 이 DB 는 일반 필지 `0`, 산 `1`(API `landCd` 2=산). 대방대림: `1159010800` + `0` + `0501` + `0000`.
- 실측: aptSeq 28,961개 중 주소 PNU 가 `apartments` 에 있는 것 21,779개(75%), 그중 기존 매핑과 다른 것 2,244개 →
  다필지 단지의 대표 필지 차이 또는 혼입. 무조건 주소 우선은 관리사무소동 등 중복 레코드 오매핑 위험이 있어 2순위로만 쓴다.
- 3순위에 fallback 매핑(아무 단지에 붙이기)은 두지 않는다. 미매핑은 기존 `register_missing_apartments` 흐름으로 단지를 등록한 뒤 재매핑한다.
- **enrich 신규 등록 거부권 (2026-10-15).** `enrich_new_apartments` 의 고유번호 키 경로는 주소 PNU 가 `apartments` 에 없으면
  새 단지로 등록한다. 등록 전에 같은 법정동(주소 PNU 앞 10자리)에 정규화 이름(`recalc_price._normalize_name`)이 키의 최빈
  단지명과 같거나, 짧은 쪽이 3자 이상이면서 한쪽이 다른 쪽을 포함하는 기존 단지가 있으면 **등록도 매핑도 하지 않고** 모호로
  분류해 로그(개수 + 최대 50건, 키별 후보 PNU)로 남긴다. 이름은 거부 근거로만 쓰고 매핑 근거로는 쓰지 않는다 — 다른 지번으로
  이미 등록된 단지가 중복 등록되는 것을 막기 위해서다(로컬: 이전 이름 매칭 키 28건 중 26건 거부). 순수 함수는
  `batch/trade/registration_veto.py`. 거부된 키는 사람 검토 후 매핑하거나 등록한다. 이름 키 경로는 바뀌지 않는다.
- **2026-10-15 변경 — 법정동 이름 매칭 순위 제거.** 원래 3순위는 같은 법정동 후보로 기존 이름 매칭 3단계(정확·포함·핵심명,
  `api_name_exact` / `api_name_contains` / `api_name_core`)였다. 로컬 검증에서 이 경로의 매핑 28건 중 절반가량이 틀렸고
  (숫자 지운 정규화 신관주공2 → 주공3, 포함 매칭 엘리시아 → 연동엘리시아), 물리 게이트는 `apt_area_type` 이 없는 단지(38%)를
  판정하지 못해 걸러내지 못했다. 그래서 고유번호 키는 상속(1)·주소 PNU(2)로만 매핑하고, 이름 근거만 있는 키는 미매핑으로 둔다.
  이미 이름 매칭으로 들어간 매핑의 재검토는 롤아웃 후 별도 이슈(`scripts/rematch_bad_mappings.py`)로 다룬다.
- 구현 위치: 새 모듈 `batch/trade/trade_key_mapping.py`. 순위 판정은 순수 함수 `decide_mapping(...)` 로 분리한다.
  기존 이름 키 매핑(`recalc_price._update_mapping`)은 그대로 둔다.

### 4-3. 과거 데이터 키 변경

**스키마 추가** (`trade_history`, `rent_history` — NULL 허용, PostgreSQL 에서 테이블 재작성 없음)

| 칼럼 | 의미 |
|---|---|
| `legacy_apt_seq TEXT` | 변경 전 원래 키. **롤백 = `apt_seq = legacy_apt_seq`** |
| `apt_seq_method TEXT` | 키 결정 방법: `api` / `infer_single` / `infer_year` / `infer_year_area` / `infer_area` / `api_backfill`, NULL = 기존 키 유지 |
| `rent_history.build_year INTEGER` | 4-1 참조 |

`api_apt_seq` 는 계속 **API 원본값만** 담는다(추론값을 넣지 않는다).

**추론 규칙** — 기존 키 L 안에서 aptSeq 가 있는 행으로 서명을 학습한다. 서명은 매매 = (준공연도[, 면적]), 전월세 = (면적).

1. 행에 aptSeq 가 있으면 그것 → `api`
2. L 의 aptSeq 가 하나뿐이고 서명이 그 aptSeq 의 관측 서명과 일치 → `infer_single`
3. L 이 혼입이면 매매는 준공연도 → 준공연도+면적, 전월세는 면적으로 **유일하게** 좁혀질 때만 → `infer_year` / `infer_year_area` / `infer_area`
4. 그 외 → 기존 키 유지(기존 매핑 그대로라 **현재보다 나빠지는 행이 없다**)

추론은 구 단위로 Python 에서 수행한다(순수 함수 `infer_keys(known_rows, target_rows)`). 구 하나는 매매 수만·전월세 십수만 행 수준이다.

**추론 커버리지 (로컬 실측 — 운영은 aptSeq 가 더 많아 개선 예상)**

| 구분 | 매매 (aptSeq 없음 271.6만) | 전월세 (aptSeq 없음 592.0만) |
|---|---|---|
| 단일 키, 서명 일치 | 244.1만 (89.9%) | 521.6만 (88.1%) |
| 혼입 키, 준공연도로 유일 | 8.1만 (3.0%) | — |
| 혼입 키, 준공연도+면적 / 면적으로 유일 | 1.1만 (0.4%) | 16.8만 (2.8%) |
| **혼입 키, 추론 불가 → API 잔여 수집** | **0.9만 (0.3%)** | **3.1만 (0.5%)** |
| aptSeq 미관측 키 / 단일 키 서명 불일치 → 기존 키 유지 | 17.4만 (6.4%) | 50.6만 (8.6%) |

**API 잔여 수집** — 혼입 키의 추론 불가 행이 있는 (구, 월)만 대상: 매매 2,134 + 전월세 4,939 ≈ **7,100콜(약 8일)**.
`backfill_trades` 의 체크포인트·보조키 구조를 재사용하고, API 응답 행을 중복 판정 키로 DB 행과 대응시켜
`api_apt_seq`·`apt_seq` 를 채운다(`api_backfill`).

### 4-4. 운영 반영 순서

각 단계는 독립 머지·배포 가능하고, **중간에 멈춰도 데이터가 현재보다 나빠지지 않는다.**

| 단계 | PR | 내용 | 실행 |
|---|---|---|---|
| 1 | 적재·매핑 전환 | 4-1·4-2 + 스키마 칼럼 + 동기화 칼럼 추가(`api_apt_seq`, `legacy_apt_seq`, `apt_seq_method`, `dealing_gbn` 등) | 배포 시 `create_tables()` 의 `ALTER … ADD COLUMN IF NOT EXISTS` 로 운영 스키마 자동 반영. **이후 새 혼입 중단** |
| 2 | `batch/rekey_trades.py` | 4-3 추론 키 변경 | 로컬 `--dry-run` → 로컬 적용·검증 → 사용자가 Railway `--dry-run` → `--apply`(구 단위 체크포인트) |
| 3 | 백필 대상 모드 | 4-3 API 잔여 수집 | GitHub Actions, 보조키 900콜/일 × 약 8일 |
| 4 | 마무리 | 로컬 정합 + 문서 | 사용자가 `sync_from_railway --mode full`(실행 전 로컬 전용 변경 확인 — 현재 `apt_facility_summary` 로컬 +104행), ADR-015 Accepted, 런북·`web/backend/CLAUDE.md` 갱신 |

- 1단계 후: 한 단지 거래가 기존 키(과거)와 aptSeq 키(신규)로 나뉘지만 둘 다 같은 PNU 로 매핑돼(4-2 1순위) 상세·점수는 변하지 않는다.
- 2단계 동시성: 거래 배치(`batch-trade.yml`, 매일 12:00·00:00 KST, 약 15분)와 겹치지 않게 사이 시간에 실행하고,
  스크립트가 PostgreSQL advisory lock 으로 배치와 상호 배제한다.
- 2단계 후 가격 점수는 다음 거래 배치의 `recalc_price`(매핑+전체 재계산)가 자동 갱신한다.
- 운영 메모리 1GB 캡: 대량 UPDATE 로 인한 bloat 를 줄이려 구 단위 커밋 + 대형 구 후 `VACUUM`. 사용자 실행 전 로컬에서 실행 시간·용량을 측정해 공유한다.
- 2026-10-13 로컬 임시 분리(`11590_대림아파트(411)`, `manual_fix`)는 동기화(upsert 모드인 `trade_apt_mapping`·`apt_price_score`)로 사라지며 2단계 결과로 대체된다.

### 4-5. 검증·테스트·롤백

**단위 테스트** (`scripts/tests`, DB·네트워크 없음, CI)
- `resolve_trade_key`: aptSeq 있음 / 없음 / 빈 문자열
- `infer_keys`: 단일 일치·불일치, 혼입의 준공연도 / 준공연도+면적 / 면적 해소, 모호 시 유지, 전월세 준공연도 없음
- `decide_mapping`: 1~3순위 각각, 3순위 미매핑(동명 후보만 있는 키도 미매핑), 혼입 키의 기존 PNU 가 주소 일치 aptSeq 로 가는지
- `register_missing_apartments`: 새 키 형식에서 시군구를 `sgg_cd` 로 읽는지

**적용 후 검증** (로컬 → 운영, 구 단위·전체)
1. 행 수 보존 — 두 테이블 전체 행 수 불변
2. 매핑 손실 없음 — 미매핑 행 수 미증가
3. 귀속 변화는 혼입 키에서만 — PNU 별 거래 수가 바뀐 단지가 전부 혼입 키 연루 단지. 허용 목록에는 이번 실행에서
   새로 만든 비상속 매핑의 도착 PNU 와, 그 매핑(물리 게이트 통과)으로 행을 보낸 이름 키의 출발 PNU(F3b)를 더한다
4. 기준 사례 — 대방대림 1993년 600건 / 상도1동대림 1995년 130건
5. `batch/trade/audit_mappings` 위반 수 미증가 — 귀속 보존 키(옮겨진 행이 전부 같은 PNU 를 유지한 새 키)는 기존 오매핑이
   드러난 것이므로 비교에서 빼고 재매칭 검토 목록으로 남긴다(F3a). 대칭 규칙: 이름 키는 행이 **전부** 보존 키로 갔을 때만
   기준선에서 빼고, 보존 키의 변경 후 위반은 그 키의 이름 키가 **전부** 기준선에서 빠졌을 때만 뺀다 — 한쪽만 빼면 남은
   기준선 위반이 비보존 키의 신규 위반을 가린다
6. 다음 배치 재계산 후 가격 점수 변화 상위 단지 리포트(사람 확인)

**롤백** — 1~5 중 하나라도 실패하면 해당 구를 롤백한다: `apt_seq = legacy_apt_seq`, `apt_seq_method = NULL`,
그 구에서 생성한 aptSeq 키 매핑 삭제. 체크포인트가 롤백 구를 기록해 재실행 시 건너뛴다.

**상시 감시** — 적재 배치 로그에 매핑 실패 aptSeq 키 개수·목록, 기존 신규 키 감사(`audit_mappings`) 위반 수.

## 5. 위험

| 위험 | 대응 |
|---|---|
| 잘못된 추론으로 다른 단지에 귀속 | 유일하게 좁혀질 때만 변경, `legacy_apt_seq` 로 구 단위 롤백, 검증 3·5 |
| 운영 대량 UPDATE 로 bloat·메모리 압박 | 구 단위 커밋 + VACUUM, 로컬 사전 측정 |
| 배치와 동시 실행 | advisory lock + 실행 시간대 |
| aptSeq 가 행정구역 개편 등으로 바뀜 | 키는 불투명 문자열, 같은 PNU 로 여러 키 매핑 허용(`trade_apt_mapping.apt_seq` PK, `pnu` 비유일) |
| aptSeq 미관측 키의 숨은 혼입 | 범위 밖으로 기록 — 필요 시 3단계 대상을 넓혀 후속 처리 |
| 로컬 전용 변경 유실(full sync) | 4단계 실행 전 확인 |
