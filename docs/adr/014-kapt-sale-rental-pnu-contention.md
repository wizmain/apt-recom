# 014. K-APT 분양·임대 레코드의 PNU 경합 — PNU 당 1건 유지, 분양 우선, 세대수는 합산

- **상태**: Accepted
- **날짜**: 2026-09-20

## 맥락

`apt_kapt_info` 는 PK 가 `pnu` 라 **PNU 하나에 K-APT 레코드 하나**만 붙는다. 그런데 분양·임대 혼합
단지는 K-APT 단지코드가 따로 있다.

| 단지코드 | 단지명 | 분양형태 | 세대수 | 지번주소 |
|---|---|---|---|---|
| A10045302 | 신당남산타운(분양) | 분양 | 3,116 | 중구 신당동 844 |
| A10045301 | 신당남산타운임대 | 임대 | 2,034 | 중구 신당동 844 |

적재(`ingest_full_kapt` Phase C)는 PNU 충돌 시 **먼저 들어온 쪽을 유지하고 나중 것을 건너뛴다.**
분양형태를 비교하는 규칙이 없어, 임대 레코드가 먼저 자리를 잡으면 분양 레코드는
`KAPT_<단지코드>` 더미 PNU 에 남는다(`collect_kapt_info` 가 미매핑 코드에 부여하는 키).
실측: `KAPT_A10045302`(분양 3,116세대) ↔ 실제 PNU `1114016200008440000`(임대 2,034세대).

### 영향 (2026-09-20 로컬 DB 실측)

임대 레코드가 실제 PNU 를 차지하면 그 단지의 K-APT 유래 값이 전부 임대 기준이 된다.

1. **추천 모집단에서 제외된다.** `services/apartment_eligibility.py` 의 임대전용 제외 가드가
   `sale_type='임대'` 로 단지를 뺀다(`routers/nudge.py`). 남산타운·SK북한산시티·옥수삼성 같은 대단지가
   넛지 추천에 나오지 않는다 — 가드 조건과 DB 값에서의 추론이며 API 응답으로는 아직 확인하지 않았다.
2. **세대수가 틀린다.** `apartments.total_hhld_cnt` 가 임대동 세대수로 덮인다
   (남산타운 2,034 / 옥수삼성 330 / 래미안월곡 288).
3. **주택형·관리비가 틀린다.** `apt_area_type` 이 임대 주택형(32.76㎡)만 갖고, `apt_mgmt_cost` 도
   임대 레코드 기준으로만 적재된다(로더가 `apt_kapt_info ⋈ apartments` 로 대상을 잡는다).
4. **매핑 감사가 오탐을 낸다.** `audit_mappings` 전량 실행 위반 1,756건 중 면적 단독 위반 368건의
   204건(실적 7.4만건)이 거래명=단지명인 같은 단지다. 감사 위반 수를 오매핑 규모로 읽을 수 없다.

`sale_type='임대'` 1,967 PNU 중 매매 거래가 있는 곳이 140, 10건 이상이 111곳(매매 37,858건)이다.

### 이 ADR 이 다루는 범위

`scripts/kapt_rental_swap_candidates.py`(읽기 전용)로 더미의 분양·혼합 레코드와 실제 PNU 의 임대
레코드를 **주소**로 이은 결과:

| 신뢰도 | PNU | 근거 |
|---|---|---|
| HIGH | 40 | 주소 일치 + **이름 관계** + 실거래 면적이 분양 레코드 주택형과 일치 + 1:1 |
| MEDIUM | 41 | 주소 일치이나 이름이 다름(16), 면적 근거 없음 또는 후보 복수 |
| LOW | 4 | 주소는 같으나 면적 불일치 — 다른 단지일 가능성 |

**이름 관계는 HIGH 의 필수 조건이다.** 처음에는 주소+면적만으로 HIGH 56곳을 잡았는데, dry-run 에서
이름이 다른 16곳이 전부 **이웃한 다른 단지**로 드러났다 — `하남주공1단지`(임대) ↔ `하남주공2단지`
(분양), `보라1단지` ↔ `보라2단지`. 같은 모필지를 쓰는 주공 단지들이라 주소가 겹치고 거래 면적도 맞는다.

HIGH 40곳은 전부 면적 일치율 1.00 이다. 나머지는 성격이 다르다
(분양 레코드가 다른 실제 PNU 에 있는 경우, 분양전환된 옛 임대, 임대전용에 오매핑 거래가 붙은
청년주택류). **이 ADR 의 범위는 더미로 밀린 분양 레코드가 있는 경우뿐이다.**

## 검토한 대안

**A. 제외 가드 완화 — "임대 + 매매 N건 이상이면 통과" (기각)**
경계가 없다. 매매 1~9건 29곳·10~49건 31곳·50건 이상 80곳인데 청년주택이 전 구간에 있다
(`루미노816청년안심주택` 1건, `퀸즈W청년안심주택` 13건, `라봄성동청년안심주택` 31건,
`장안동 청년주택 하트리움` 66건). 어떤 N 도 청년주택을 통과시키거나 혼합 단지를 막는다.
가드가 막으려던 대상이 새는 데다, 세대수·주택형·관리비 오류는 그대로 남는다. 데이터 오류를
추정으로 덮는 폴백이다.

**B. 단지코드 접두(앞 7자리)로 형제 레코드 찾기 (기각)**
`A100453`01/02 처럼 맞는 사례가 있으나 이웃 단지가 같은 접두를 공유한다. 실측 837 PNU·2,474쌍으로
과매칭이고 111곳 중 59곳만 설명한다.

**C. `apt_kapt_info` 를 PNU 당 1:N 으로 (보류)**
혼합 단지를 가장 정확히 표현하지만, 이 테이블을 `pnu` 1:1 로 조인하는 소비자가 넓다 — 넛지 모집단,
상세, MCP, 관리비 로더, 매핑 감사, Railway 동기화. PK 변경은 이 전부의 조인 의미를 바꾼다.
혼합 단지에서 사용자가 보는 값(매매 대상 주택형·세대수)은 분양 레코드 하나로 충분하므로, 얻는 것에
비해 영향 범위가 크다. 임대동 정보를 화면에 보여줄 요구가 생기면 그때 다시 검토한다.

## 결정

**PNU 당 K-APT 레코드 1건을 유지하고, 같은 PNU 를 두고 경합하면 분양·혼합 레코드가 이긴다.**
밀려난 임대 레코드는 지우지 않고 `KAPT_<단지코드>` 더미로 옮긴다(현재 분양 레코드가 있는 자리와 대칭).
**단지 세대수는 분양+임대 합산으로 표기한다**(2026-09-20 결정 — 아래 "세대수 표기" 근거).

### 0. 동반 레코드 — `apt_kapt_info.parent_pnu`(신규 컬럼)
더미로 옮겨진 임대 레코드가 **같은 단지의 임대동**이면 `parent_pnu` 에 그 단지의 실제 PNU 를 적는다.
이 연결이 있어야 합산이 유지된다 — 적재(Phase A)는 매번 세대수를 "그 PNU 에 붙은 레코드"의 값으로
덮어쓰므로, 연결 없이 교체만 하면 다음 월간 적재에서 분양 세대수로 되돌아간다.
- 스키마: `web/backend/database.py` `create_tables()` 의 `ADD COLUMN IF NOT EXISTS` + 부분 인덱스.
  백엔드 기동 시 실행되므로 Railway 는 배포로 컬럼이 생긴다.
- 합산: `companion_records.apply_combined_households` — `ho_cnt + SUM(동반 ho_cnt)`. 현재 값에 더하지
  않고 다시 계산하므로 멱등이다. 적재 Phase A 마지막과 교정 도구가 호출한다.
- **연결은 근거가 있을 때만 한다.** 자리를 내주는 임대 레코드가 이웃한 다른 단지인 경우가 있다
  (`군자주공14단지` PNU 의 `안산군자13단지`, `제주삼화6차부영` 의 `제주삼화LH3단지`). 연결하면 두 단지의
  세대수가 합쳐진다. 이름 관계는 같은 단지의 **충분조건일 뿐**이라(`돈암한신한진` ↔ `동소문한진임대` 는
  카카오맵으로 같은 단지임을 확인했는데 이름이 다르다) 자동 판정이 안 되는 건은 사람이 정한다.

### 1. 경합 규칙 — 한 곳에 둔다
`batch/kapt/pnu_contention.py`(신규)에 순수 함수로 둔다. 적재와 교정 도구가 같은 규칙을 쓴다.

```
resolve_contention(existing_sale_type, incoming_sale_type) -> "keep_existing" | "replace"
  분양·혼합  vs 임대        → 분양·혼합이 이긴다
  그 외 (같은 등급, 미상 포함) → 기존 유지 (현행과 동일)
```
우선순위 값(`분양`·`혼합` > `임대`)은 모듈 상수로 두고 단위 테스트로 고정한다(`scripts/tests`, DB 불요).

### 2. 재발 방지 — `ingest_full_kapt` Phase C
PNU 충돌 시 건너뛰기 전에 `resolve_contention` 을 본다. `replace` 면 기존(임대) 레코드를 더미 PNU 로
옮기고 들어오는 레코드를 실제 PNU 에 붙인다. 교체는 로그와 errors 파일에 남긴다 — 조용히 바뀌지 않게.

### 3. 기존 데이터 교정 — `scripts/swap_kapt_sale_rental.py`(신규)
- 입력은 검수 목록 CSV. **HIGH 만 대상**이고, 사람이 목록을 확인한 뒤 실행한다. MEDIUM 은 개별 확인 후
  목록에 수동 승격, LOW 는 대상이 아니다.
- CSV 의 `combine_households` 가 합산 여부를 정한다. 두 K-APT 이름이 이어지면 `yes`(자동, 31곳),
  아니면 `review` — 사람이 판정한다. `yes` 가 아니면 교체는 하되 연결하지 않아 세대수가 분양
  세대수로 들어간다(임대 세대수보다 정확하고, 추정으로 두 단지를 더하지 않는다).
- **사람의 판정은 `scripts/kapt_swap_decisions.yaml`(추적 파일)에 근거와 함께 둔다.** 검수 목록 CSV 는
  매번 다시 생성되고 `*.csv` 는 gitignore 대상이라 거기에 적으면 사라진다. 생성기가 이 파일을 읽어 자동 판정보다 우선 적용하고,
  yes/no 가 아닌 값이 있으면 중단한다. 2026-09-20 판정 9곳(카카오맵 장소 상세 + K-APT 주소·사용승인일·
  시공사 대조): **yes 6** — 돈암한신한진·방화2-2 그린·벽산라이브파크·문촌마을7단지(카카오 세대수가
  합산과 일치), 서울숲한신더휴·남가좌동현대(카카오는 임대동을 별도 장소로 두지만 도로명·사용승인일이
  같고 장소명이 같은 단지). **no 3** — 래미안월곡(`월곡3SH-vill` 은 사용승인일·시공사가 다른 별도 SH
  임대동), 군자주공14단지(`안산군자13단지`), 제주삼화6차부영(`제주삼화LH3단지`).
- 기본 dry-run, `--apply` 로 반영, `--target local|railway`. 한 PNU 의 교체는 한 트랜잭션.
- PNU 1건당 하는 일
  1. K-APT 유래 네 테이블(`apt_kapt_info`·`apt_area_type`·`apt_area_info`·`apt_mgmt_cost`)의 임대 행을
     `KAPT_<임대코드>` 로 옮긴다. **반드시 먼저** — 분양을 먼저 옮기면 실제 PNU 의 PK 와 충돌한다
  2. 같은 네 테이블의 분양 행(`KAPT_<분양코드>`)을 실제 PNU 로 옮긴다
  3. `apartments`: `total_hhld_cnt`·`dong_count`·`max_floor`·`use_apr_day` 를 분양 레코드 값으로,
     연결된 경우 세대수를 합산으로 올린다
  - **지우는 행이 없다.** 초안은 임대 기준 관리비를 삭제한다고 했으나, 외래키가 없고 더미 키가 비어
    있어 옮기는 쪽이 낫다 — 데이터가 보존되고 같은 함수로 역교환된다. 실제 PNU 의 관리비는 비게 되므로
    `collect_mgmt_cost --source xlsx` 재적재로 분양 기준을 채운다
  - 네 테이블은 HIGH 전 PNU 에서 K-APT 유래(`apt_area_info.source='kapt_area'`)임을 확인했다. 시설·가격·
    안전 등 위치·거래 기반 테이블은 필지에 속하므로 건드리지 않는다
- 가격점수는 거래 기반이라 영향 없다. `recalc_price` 의 면적 범위 필터가 `apt_area_info` 를 쓰므로
  다음 12h 배치에서 필터 범위가 분양 주택형으로 바로잡힌다.

### 4. 제외 가드는 그대로 둔다
`sale_type` 이 바로잡히면 가드는 의도대로 동작한다. 가드에 예외 목록·임계값을 넣지 않는다.

## 근거

- **원인을 고친다.** 문제는 가드가 아니라 잘못 붙은 레코드다. 레코드를 바로잡으면 추천 누락·세대수·
  주택형·관리비·감사 오탐이 함께 풀린다.
- **짝짓기 근거가 물리적이다.** 주소 일치만으로 짝을 만들고, 그 PNU 의 실거래 면적이 분양 레코드의
  주택형과 맞는지로 검증한다. 매핑 감사(`mapping_checks.area_match_ratio`)와 같은 판정 기준이라
  두 도구의 결론이 어긋나지 않는다.
- **되돌릴 수 있다.** 임대 레코드를 지우지 않고 더미로 옮기므로 같은 도구로 역교환이 가능하다.
- **영향 범위가 좁다.** PK·소비자 조인을 건드리지 않는다. 스키마 변경은 NULL 허용 컬럼 1개 추가뿐이다.

## 결과

- 추천 모집단에 혼합 단지 40곳(HIGH)이 돌아온다. 세대수가 단지 규모로 바뀌어 `min_hhld` 필터 결과도
  달라진다.
- **세대수 표기 — (나) 합산으로 결정 (2026-09-20).** 교체만 하면 세대수가 "분양 세대수"가 된다(남산타운
  2,034 → 3,116, 단지 전체 5,150 아님). 카카오맵 장소 상세와 대조한 결과(2026-09-20, 표본 4곳):

  | 단지 | 현재 DB | K-APT 분양 | K-APT 임대 | 분양+임대 | 카카오맵 |
  |---|---|---|---|---|---|
  | 신당남산타운 | 2,034 | 3,116 | 2,034 | 5,150 | **5,152** (49㎡ 2,034세대 포함) |
  | 옥수삼성 | 330 | 1,114 | 330 | 1,444 | **1,444** (45㎡ 330세대 포함) |
  | 돈암한신한진 | 580 | 3,929 | 580 | 4,509 | **4,515** (45A·45B 580세대 포함) |
  | SK북한산시티 | 1,497 | 3,830 | 1,497 | 5,327 | **3,830** (임대는 별도 POI `…(1353-1)`) |

  현재 값은 4곳 모두 카카오와 다르다. 3곳은 카카오가 **분양+임대 합산**으로 표기하고(차이 0~6세대),
  1곳은 임대동을 별도 장소로 나눠 **분양만** 표기한다. 즉 "분양 세대수"도 "합산"도 카카오와 전부
  일치하지는 않는다. 선택지:
  - (가) `total_hhld_cnt` = 분양 레코드 세대수 — 매매·추천 대상 규모. 카카오와는 1/4 일치
  - (나) `total_hhld_cnt` = 분양+임대 합산 — 사용자가 아는 "단지 규모"에 가깝고 카카오와 3/4 일치.
    짝지어진 임대 레코드의 `ho_cnt` 를 더하면 되며 `min_hhld` 필터 의미도 "단지 규모"로 일관된다
  - 어느 쪽이든 세대당 관리비의 분모는 `apt_kapt_info.ho_cnt`(관리비를 보고한 그 레코드의 세대수)를
    그대로 쓴다 — 표기용 세대수와 섞지 않는다
  표본이 4곳뿐이라 카카오의 합산/분리 기준(필지 동일 여부로 추정)은 단정하지 않는다.
- 실제 PNU 의 관리비 이력이 한 번 빈다(임대 기준 행은 더미로 옮겨 보존, 분양 기준은 재적재로 채운다).
- `apt_vectors`(ML 벡터)가 세대수·면적을 피처로 쓴다면 재생성 전까지 옛 값 기준이다 — 미확인.
- 매핑 감사의 면적 오탐이 줄어, 남는 위반이 실제 오매핑에 가까워진다.
- Railway 반영은 기존 관행대로 사용자가 직접 실행한다(`--target railway --apply`).

### 검증
1. 교체 전후 `audit_mappings --pnu-file <HIGH 목록>` — 면적 위반이 사라지는지
2. 교체한 PNU 가 `POST /api/nudge/score` 결과에 나오는지. 교체 전 제외는 가드 조건과 DB 값
   (`sale_type='임대'`)에서 추론한 것이라, **교체 전 응답을 먼저 떠서 실제로 빠져 있는지 확인**한다
3. `kapt_rental_swap_candidates` 재실행 시 HIGH 가 0 이 되는지 (멱등)
4. 로컬 dry-run(트랜잭션 안에서 실제 교체 후 롤백) 결과: 40건 교체·거부 0건, 합산 37(자동 31 + 판정 6)·합산 안 함 3

### 범위 밖 (별도 백로그)
- 분양 레코드가 **다른 실제 PNU** 에 있고 거래만 임대 PNU 에 붙은 경우 → 거래 재매핑
  (`scripts/rematch_bad_mappings.py` 흐름)
- 분양전환된 옛 임대(K-APT 만 '임대') → 개별 판정
- 임대전용에 오매핑 거래가 붙은 경우(청년주택류), `유원제일` 같은 NO_TARGET 오매핑 → 매핑 해제 검토
- LOW 4곳(`연수1차시영임`·`전농동아` 등) — 주소는 같으나 면적이 어긋나 원인 미상
