# 인스타 데일리 파일럿 런북 (Phase 0)

- 대상 PRD: `docs/prd/2026-07-24-instagram-daily-content.md`
- 목적: **운영 가능성·계측 정상성 검증**(2주·14회 수동 발행). 콘텐츠 성과 판정 아님(포맷 단위 관찰만).
- 도구: `scripts/insta_cards/rotation.py`(리졸버, read-only) + `rotation.yaml`(설정) + 기존 생성기.

## 매일 절차 (개입 목표 ≤ 5분)

1. **오늘 배정 확인**
   ```
   .venv/bin/python -m scripts.insta_cards.rotation
   ```
   → 그날 `series`·`slug`·생성 명령이 출력된다. (전체 표: `--calendar 14`)

2. **dry-run 검증** (데이터 충분한지 먼저 확인 — PRD §9-3)
   출력된 `run` 명령 끝에 `--dry-run` 을 붙여 실행. 후보 부족/빈 결과면 **오늘 slot skip 또는
   `rotation.yaml` 큐의 다음 후보로 수동 대체**(조용한 축소 금지). value 자치구 키워드가 결과가
   적으면 더 넓은 키워드로 조정.

   **개수만 보지 말고 단지명·가격대를 눈으로 확인할 것.** 1일차(2026-07-25)에 강남구 value 가
   ㎡당 825~933만원의 "가성비 TOP5"를 뽑았는데 전부 전용 20~55㎡ 오피스텔·도시형생활주택이었다.
   → `min_smallest_area`(모든 주택형이 N㎡ 이상) 필터를 추가해 해소. 다른 시리즈에서도
   **훅과 실제 물건이 어긋나는지**가 검수의 핵심이다.

3. **생성 + 프론트 반영**
   `--dry-run` 없이 실행 → 다시 `--publish` 로 실행하면 posts.json·커버·IG 자산·content_index 가
   갱신된다(로컬 파일, "커밋 필요" 상태). **`--publish` 는 배포가 아니다.**

4. **브랜치 → PR → 머지** (main 직접 push 금지)
   ```
   git switch -c content/ig-YYYYMMDD
   git add web/frontend-next/src/content/instagram/ web/frontend-next/public/content/ web/backend/content/content_index.json
   git commit -m "content(ig): {slug} 발행"
   git push -u origin content/ig-YYYYMMDD && gh pr create ... && gh pr merge --merge
   ```

5. **배포 완료 확인** → **게시**
   머지 후 Cloudflare(웹) 배포가 끝나면, **자산 200 만 보지 말고 `latest.json` 의 generation 이
   로컬과 일치하는지까지 확인한다.**
   ```
   # 로컬 generation
   cat web/frontend-next/public/content/instagram/{slug}/ig/latest.json
   # 원격 generation (같은 값이어야 한다)
   curl -s https://apt-recom.kr/content/instagram/{slug}/ig/latest.json
   ```
   일치하면 게시:
   ```
   .venv/bin/python -m scripts.insta_cards.instagram {slug}
   ```
   `verify_assets` 가 원격 200/jpeg/8MB 를 강제하므로, 배포 전이면 게시가 실패한다(안전망). 실패 시
   배포 완료를 기다렸다 재실행.

   **왜 generation 까지 보나 (2026-07-29 3일차 실측)**: `latest.json` 의 캐시 헤더가
   `max-age=31536000, immutable, no-cache` 라 revalidate 에 의존한다. 머지 직후 게시하면 엣지에 따라
   **이전 generation 을 받아** 새 자산 URL 이 404 가 되고 게시가 막힌다. 그때 재생성·재발행을
   시도하지 말고 **몇 분 뒤 같은 명령을 재실행**하면 된다(원인은 캐시, 자산은 정상).
   재생성으로 우회하면 generation 이 또 바뀌어 같은 문제를 반복한다.

6. **(선택) 스토리 리마인드** — 프로필 링크는 **고정 `/content` 인덱스**라 매일 갱신 불필요.

## 게시 실패처럼 보이는 성공 (2026-08-05·06 수정)
rate limit **403** 이 4일 연속(8/3~8/6) 발생했고, **매번 게시는 성공했는데 로그가
`published_pending` 에 멈춰** 원격을 확인해 수기 보정해야 했다. 403 이 터지는 지점은 두 군데다.

| 지점 | 발생 | 처리 |
|---|---|---|
| `media_publish` **직후 permalink 조회** | 8/3·8/4·8/5 | `published` 기록 + `permalink_error` 에 사유 (`_try_fetch_permalink`) |
| `media_publish` **자체** | 8/6 | 원격 확인 후 게시됐으면 `published` 기록 (`_resolve_uncertain_publish`) |

**핵심: 이 API 에서는 "예외 = 실패"가 성립하지 않는다.** `media_publish` 가 403 을 반환하고도
게시는 처리된다(8/6 실측). 그래서 실패 시 곧바로 단정하지 않고 `find_published_media` 로 원격을 본다.

- 게시돼 있으면 → `published` 기록(사유는 `note`), 재실행 불필요
- 원격에도 없으면 → 원래 예외를 올린다(진짜 실패)
- **확인 조회까지 막히면** → 상태 불명이므로 중단하고 `--check` 를 안내한다. 임의로 성공·실패를
  단정하지 않는다

**원칙**: 게시 성공 사실의 기록이 부가 정보 조회 실패로 유실되면 안 된다. 로그가 pending 인 채로
끝났다면 재실행 전에 반드시 `--check` 로 실게시 여부를 먼저 본다(`--force` 재실행은 자식
컨테이너부터 다시 만들어 **중복 게시**가 된다).

판정 기준(캡션의 랜딩 URL 마커)은 `client.find_published_media` 하나로 유지한다 — 자동 확인과
`--check` 가 다른 기준을 쓰면 안 된다. 마커는 `site_url` 을 따라가므로 도메인을 하드코딩하지 않는다.

## 데이터 품질 가드 (2026-07-25 추가)
- **value 시리즈는 `--min-smallest-area` 가 필수**다. `rotation.yaml` 의
  `series.value.min_smallest_area`(현재 59)가 정책값의 단일 출처이며, 리졸버가 명령에 자동으로
  실어준다. 인자를 빼면 CLI 가 실패한다(조용히 약한 필터로 돌아가지 않음).
- 의미: `min_area`(주택형 **하나라도** N㎡ 이상)와 방향이 반대인 **모든 주택형이 N㎡ 이상**.
  오피스텔 단지는 소형 주택형이 섞여 `min_area` 로는 걸러지지 않는다.
- 같은 필터가 `map_cta.filters` 에도 실려 랜딩 TOP5 와 지도 재계산 모집단이 일치한다.

- API 가 하한을 무시하면 `verify_min_households` 가 발행을 중단시킨다(조용한 약화 금지).
- **큐 순서 주의**: compare 큐 0번은 파일럿 직전 수동 발행분(2026-07-17 마포 vs 성동)과 겹쳐

## 데이터 품질 가드 — 시리즈별 정책값 (2026-07-29 정렬)
정책값의 단일 출처는 **`rotation.yaml` 의 `series.{시리즈}.*`** 이고, 리졸버가 명령에 자동으로 실어준다.
CLI 기본값에 기대지 않는다 — 기본값이 바뀌면 어느 카드가 어떤 하한으로 나갔는지 추적할 수 없다.

| 시리즈 | 정책값 | 카드 공시 |
|---|---|---|
| `trade_top` | `min_hhld: 100` | 조건 + 방법론 |
| `value` | `min_hhld` + `min_smallest_area: 59` + `min_area/max_area: 60~85` | 조건 + 방법론 + `map_cta.filters` |
| `compare` | `min_hhld: 100` | 조건 + 방법론 + `map_cta.filters` |
| `lifestyle` | `min_hhld: 100` + `min_smallest_area: 59` | 조건 + 방법론 + `map_cta.filters` |
| `budget_choice` | `min_hhld: 100` + `min_budget_ratio: 0.8` | 조건 + 방법론 + `map_cta.filters` |

**적용과 공시는 별개다.** lifestyle 은 하한을 적용하면서도 카드에 표기하지 않고 있었다(2026-07-29 정렬).
가드를 추가할 때는 payload·검증·조건·방법론·`map_cta.filters` 다섯 곳을 함께 본다.

**세대수 하한은 면적 하한을 대체하지 못한다 (2026-07-30 4일차 실측).** 강남 반려동물 4위로
한화진넥스빌(294세대)이 올라왔는데 전 주택형이 전용 35~51㎡였다. 23~34억 단지 사이에 4.6억으로
실려 랭킹이 임의로 보였다. → lifestyle 도 `min_smallest_area`(현재 59) 필수. **두 하한은 걸러내는
대상이 다르다**: `min_hhld` 는 빌라급(세대수 적음), `min_smallest_area` 는 소형 전용 단지(세대수 많음).
주택형 하한은 nudge/score 응답에 대응 필드가 없어 사후 검증이 불가하다(`min_hhld` 만 검증) — API 적용을
신뢰하는 대신, 검수 때 **단지 전체 주택형 범위**를 눈으로 확인한다.

**"예산 이하"는 "같은 예산" 훅을 보장하지 못한다 (2026-07-31 5일차 실측).** 6억 카드의 대표로
2.85억(노원 씨엠, 10세대)·1.96억(기흥글로리아)이 뽑혔다. 두 결함이 겹친 결과다:
① 예산·면적 밴드는 단지 규모와 무관해 빌라급이 대표로 뽑힌다 → `min_hhld` 를 budget_choice 에도
적용(초기 "해당 없음" 전제 정정). ② cost 넛지는 싼 물건을 위로 올리므로 "예산 이하" 조건에서는
**구조적으로 예산 하단이 대표가 된다** → `min_budget_ratio`(현재 0.8) 로 대표 거래를 예산의
80~100% 구간으로 제한. 이건 가드가 아니라 **선정 기준**이다 — 시리즈 의도를 "예산으로 살 수 있는
대표 매물 비교"로 확정했다. 예산 칩도 상한이 아닌 구간(`4억 8,000만원~6억`)으로 공시한다.
`min_hhld` 는 응답으로 사후 검증하고(`verify_min_households`), 예산 구간은 적격 집합 SQL 에서
강제되므로 카드 표기 가격이 구간을 벗어날 수 없다.

**하한만으로는 "가성비" 랭킹이 성립하지 않는다 — 비교 면적을 고정해야 한다 (2026-08-01 6일차 실측).**
서초 value TOP5 가 전부 전용 95~244㎡·6.5~27억 대형이었다. `min_smallest_area` 는 소형 오피스텔만
막을 뿐, **대형 평형은 ㎡당 단가가 구조적으로 낮아**(면적 할인) ㎡당 오름차순 정렬이 대형 편중 단지를
자동으로 상위에 올린다. 서초 실측: 110㎡~ 2,152만원/㎡ vs 60~85㎡ 3,106만원/㎡.

- 순위는 `apt_price_score.price_per_m2`(단지 전체 평균)가 아니라 **밴드 내 거래만으로 계산한
  ㎡당 평균**으로 매긴다(`value.fetch_band_price_per_m2`). 질문을 "같은 크기 집, 어디가 싼가"로 고정.
- 창은 **180일**이다(다른 시리즈는 90일). 밴드 한정이라 표본이 1/4로 줄어 90일에는 용산이 5건
  (=TOP5 와 동일)이라 한 건만 빠져도 발행이 중단된다. 밴드 내 **2건 이상**인 단지만 후보.
- **카드에 총액·전용면적을 병기한다.** ㎡당 가격만 보이면 독자가 물건 크기를 알 수 없어 대형 고가를
  저렴하다고 읽는다. 다른 시리즈는 모두 총액을 보여주는데 value 만 빠져 있었다.
- **기준 변경 이력**: 2026-07-31 이전 발행분(7/18 서울, 7/28 강남)은 **단지 전체 평균 ㎡당 가격**
  기준이라 같은 지역이라도 순위가 다르다. 이미 게시된 카드는 재발행하지 않는다(게시 로그상 중복).
  7/28 강남도 같은 편중이 있었다 — 전용 60~179㎡·4.77~32.5억, 5곳 중 3곳이 106㎡ 이상.

## 문구 오버라이드 (2026-07-29 추가)
- 템플릿 문구가 데이터를 오해하게 만들 때만 `--copy-file` 을 쓴다. 파일은 **추적되는 경로**
  `scripts/insta_cards/copy_overrides/{slug}.yaml` 에 두고 콘텐츠 PR 에 함께 커밋한다
  (`reports/insta/` 는 gitignore 라 재현이 안 된다).
- 오버라이드 본문에 **숫자를 다시 적지 않는다**. 비교표·랭킹에 이미 병기되므로, 재생성으로 값이
  움직이면 문구만 낡는다.
- 허용 키는 `hook`·`why`·`fit_for` 뿐이며, 오버라이드 문구에도 금지어·길이 검사가 적용된다.
- **오버라이드가 같은 사유로 반복되면 생성기 규칙으로 승격한다**(개별 파일 누적 금지).
  첫 사례: 3일차 compare 의 0.1점 차 승자 표현 → **10일차(0.7점 차)에 재발해 규칙으로 승격 완료**
  (`copywriting.COMPARE_TIE_THRESHOLD`). 이후 compare 는 오버라이드 없이 자동으로 동률을 표기한다.

## budget_choice 면적 동률 (2026-08-07 수정)
`fit_for` 문구가 **고정 문자열**이라 데이터와 무관하게 "B 는 같은 예산으로 더 넓은 면적" 이라고
말하고 있었다. 두 가지가 틀렸다:

1. 두 지역에 **같은 목표 면적**(`--area-a`/`--area-b`)을 주는 구조라 대표 면적은 거의 항상 같다.
   실측(큐 6개 조합): 차이가 `0.0 / 0.1 / 0.1 / 0.5 / 0.6㎡`. 즉 "더 넓다"는 주장이 사실상 늘 거짓.
2. A 가 더 넓은 경우에도 B 를 넓다고 말한다 — 방향이 뒤집힌다.

→ `BUDGET_CHOICE_AREA_TIE_THRESHOLD`(3.0㎡) 이하면 **면적 대신 가격으로 서술**하고, 넘으면
**실제로 넓은 쪽**에 문구를 붙인다. 저렴한 쪽 판별도 가격 실측값을 따른다.
밴드가 실제로 다른 사례(2026-07-13 카드 62.7 vs 83.0)는 20㎡ 대라 임계값과 여유 있게 갈린다.

**점수형 기여 항목은 "접근" 표현에 쓰지 않는다.** cost 넛지는 1위 기여자가 `가격 점수` 라
그대로 쓰면 *"가격이 높아도 가격 점수 접근을 우선한다면"* 이라는 모순 문장이 된다.
`_first_facility` 로 시설 항목만 고르고, 없으면 점수 표현으로 바꾼다.

**이미 발행된 카드에도 있던 결함이다**(7/31·7/13). 재발행은 하지 않는다.

## compare 동률 임계값 (2026-08-05 규칙 승격)
상위10 평균 점수 차가 **1.0점 이하면 승자를 선언하지 않는다**(`COMPARE_TIE_THRESHOLD`).
임계값은 감이 아니라 **실측 분포의 단절점**이다 — 큐 8개 쌍의 차이가 이렇게 갈렸다:

```
0.0  0.6  0.7  0.9   |   2.4  2.9  4.7  5.5
```

0.9 와 2.4 사이가 자연 단절이라 1.0 을 경계로 잡았다(경계값은 동률 쪽 포함). 큐를 바꾸거나
넛지를 바꾸면 분포가 달라질 수 있으니, **임계값을 조정할 때는 같은 방식으로 분포를 다시 뽑는다.**
